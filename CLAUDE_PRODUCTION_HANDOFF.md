# Motion Retail production readiness audit and Claude handoff

Reviewed 15 November 2026 against `main` at `7f2fe8ec07a84d73cc206cc3c3ebd0d056212943`. Use this file as the implementation brief. **Hold real client data and financial operations until the release gates below are met.** The demo configuration can remain available on isolated synthetic infrastructure.

## System and audit scope

React serves the tills and back office. FastAPI enforces identity, permissions and branch scope, then runs Tryton in-process under a PostgreSQL transaction. Tryton owns stock, POS, purchasing and the posted double-entry ledger. The `motion` schema adds business approvals, idempotency, cash shifts, audit events, and sync receipts. The custom Tryton module stamps accounting moves with branch IDs. At a branch, FastAPI and SQLite accept sales during a WAN outage and push the durable outbox to central.

Keep Tryton as the system of record. Preserve atomic stock, ledger, receipt, approval consumption and audit writes. Use migrations for existing records and forward accounting corrections for posted entries. This review uses source inspection and disposable loopback PostgreSQL. The findings below distinguish source-confirmed defects from behavior that needs a regression or fault-injection test.

Concurrent workspace edits touched bootstrap retry, seed locking and batching, and sign-out cache handling during review. The line references and findings describe the committed baseline. Carry forward those edits and retest the overlapping work in M4, M5, and L1.

## Critical

### C1 · Approval resubmission discards the domain validation

**Evidence.** `api/motion_api/routes/operations.py:30–34,68–72`, `api/motion_api/services/approvals.py:191–215`. Resubmission accepts an arbitrary payload and client-supplied amount. It replaces the canonical record and uses that amount to choose the approval band. It also omits the current branch and original action permission checks. Downstream refund, payment, transfer and write-off code trusts IDs and amounts from this payload. The refund line update at `api/motion_api/services/pos.py:550–576` does not bind each line to the original receipt, and `api/motion_api/services/stock.py:346–367` trusts the write-off source and discrepancy ID.

**Impact.** A returned approval no longer reliably represents the transaction the domain validated. This undermines maker-checker controls and can move money or stock against the wrong record or approval amount.

**Fix and acceptance.** Replace generic payload editing with action-specific correction commands that call the same validators as initial submission. Bind immutable resource IDs to server-owned records, recalculate amounts, check current permission and branch, and revalidate at execution under lock. Temporarily disable correction for any workflow without a typed validator. Add explicit approval revision IDs to action history and enforce one approver per revision across steps. Review open historical requests against source records and require reapproval where canonical terms cannot be established.

### C2 · Public demo can open privileged sessions on ordinary accounts

**Evidence.** `api/motion_api/settings.py:114–129`, `api/motion_api/security.py:216–232`, `api/motion_api/main.py:50–60`, `render.yaml:19–26`. The demo setting defaults on, and a boolean conjunction is the only demo-login gate. The account query includes every active user who has completed password setup. Demo sessions are ordinary sessions and remain valid until revoked or expired. Test seeding has its own switch.

**Impact.** A misconfigured client deployment can expose ordinary staff accounts and full privileged access. Turning off the picker by itself leaves existing sessions usable.

**Fix and acceptance.** Default all demo switches off in the production blueprint, and refuse startup if anonymous demos or synthetic seeding are enabled on a client deployment. Use an isolated demo database and an explicitly marked demo-account allowlist. Track demo session origin and revoke those sessions when closing the demo. Validate that client deployment rejects both routes and seeding, while the isolated demo still works as intended. Rotate the Neon password and Render API key mentioned in the handoff through their consoles, update the scoped Render database secret, and confirm with the operator that old credentials have been revoked. Keep secret values out of logs and handoffs.

### H2 · Sale, refund, and payment retries need one idempotency contract

**Evidence.** `pos.py:270–286,411–425,550–580`, `finance.py:348–379`, `web/src/pages/Pos.tsx:294–312,390–393`. POS has a single global key namespace and an early existing-row return in the posting primitive. Checkout checks the cashier for a replay but does not verify operation, register or input equivalence. Refund mutates line quantities before calling that same primitive and marks approval consumed afterward. It generates a fresh key in the UI for every attempt. Bank deposits do not bind a unique transfer identity to the posting.

**Impact.** An ambiguous response or changed request can yield the wrong receipt, an error after a successful commit, or a refund approval recorded against an unrelated sale. Retrying a bank-slip entry can post twice when funds cover both.

**Fix and acceptance.** Use a persisted operation key, caller/terminal scope, request fingerprint and result for every money-moving command where retries are possible. Resolve the key before touching stock, line counters or approvals. Atomically claim or re-read the key under competition with stable in-progress/conflict behavior. Treat the same key and same payload as a durable receipt lookup and preserve it across reload or network failure. Verify a lost response and a simultaneous duplicate leave one business result, one set of postings and one approval transition.

### H3 · Refunds and checkout can disagree on the amount to reverse

**Evidence.** `pos.py:248–249,308–325,523–573`, `common.py:15–21`, `web/src/pages/Pos.tsx:24,149–150`. Running the actual API helper and installed Tryton line calculator for 0.001 kg at UGX 2,500/kg gave UGX 3 and UGX 2 respectively. Verify fractional and multi-line cases through the full checkout. The refund guard caps quantity but does not track remaining original gross, net, or VAT rounding residuals. Refunds use current tax rules and always pay cash. COGS at the current average is documented policy.

**Impact.** Weighted items can produce inconsistent till totals, split refunds can leave rounding residuals, and refunds after a tax change can misstate the original sale's tax reversal. Cash-only refunds can turn an unverified non-cash claim into cash if that is allowed by policy.

**Fix and acceptance.** Preview and post with one canonical calculator and exact quantities. Store per-line original gross/net/VAT and remaining refundable amounts, and allocate residuals under lock, with the final refund closing the remaining balance exactly. Define refund-to-tender and settlement rules with Finance. Reject duplicate refund lines, serialize refund reservations per original receipt, and keep current-cost COGS treatment explicit unless Finance approves a change. Cover weighted items, mixed tenders, tax/category changes, and multiple partial refunds against the original receipt and journal.

### H4 · Stock changes lack a consistent physical-inventory invariant

**Evidence.** `stock.py:186–236,240–274,307–369,373–416`, `pos.py:241–245`. Transfer receipt defaults omitted lines to fully received. Stock write-off checks shelf availability when requested but does not recheck it at execution or share the checkout stock guard. Transit write-off updates a discrepancy without verifying that it remains reserved for that approval. Late receipt moves stock but lacks an explicit Tryton state assertion, and transfer completion counts sibling discrepancies without explicitly serializing on the transfer first.

**Impact.** Uncounted goods can appear in destination stock. Stock sold after a write-off was requested can leave the source negative when the approval executes. Parallel discrepancy closures need verification to rule out a transfer stuck in discrepancy status.

**Fix and acceptance.** Require explicit counts or a separately confirmed receive-all action. Lock the transfer and affected stock keys in one documented order, use the same guard for all stock-depleting workflows, check current availability and discrepancy ownership, then verify Tryton transitions. Reconcile before/after stock across source, transit and destination for shortages, late receipts, and write-offs. Assert transfers produce zero journal entries and authorized shrinkage posts to the right branch and account.

### H5 · Three-way match uses the wrong grain for partial deliveries

**Evidence.** `purchasing.py:110–115,165–221,229–245,249–296`. Receipt maps one input per PO line and can fall back to scanning all draft moves. It edits the quantity of an existing move and relies on Tryton to regenerate the remainder. Invoice detail compares each invoice line to the entire PO line's lifetime received quantity, with no accounting for quantities previously billed. Lines without receipt evidence are skipped by `all()`. Supplier bill reference has a presence check only. PO creation resolves the approved supplier ID back through a name lookup. The payables list calculates open amount from unreconciled invoice move lines alone, which can leave the original amount displayed after partial payment.

**Impact.** Later deliveries can make correctly sized partial bills appear unmatched. The empty match case can report success without receipt evidence. Duplicate references and residuals require explicit controls.

**Fix and acceptance.** Use bounded queries through purchase-line and receipt links. Allocate each bill to specific receipts or validate invoice quantities against received minus previously billed per PO line, with approved exceptions distinguished from PO invoices. Post to the approved supplier ID, persist the supplier reference with a business-approved duplicate check, and derive each open balance from Tryton's outstanding-liability logic. Test one order received and billed in several deliveries, invoices posted in different orders, partial payments, suppliers sharing a display name, duplicate submit, and unknown or repeated lines. Tie quantities and value through stock, clearing, payables and reconciliation.

### H6 · Blanket Tryton warning suppression hides operator safety checks

**Evidence.** `common.py:39–44`, `tryton.py:174–177`. The installed Tryton implementation skips the warning decision in `trytond/res/user.py:984` when `_skip_warnings` is set or the transaction is running as root. Installed warning sites include payment term dates, future-dated invoices, tax discrepancies and likely duplicate invoices (`trytond/modules/account_invoice/invoice.py:1358,2094,2156,2188`), shipment quantity mismatches (`stock/shipment.py:331`) and purchase move quantities (`purchase/purchase.py:2079`).

**Fix and acceptance.** Classify warnings reachable from the workflows. Turn invariants into service validation and represent legitimate exceptions as an explicit, authorized, audited confirmation. Use mapped operators for interactive writes. Keep fixture exceptions narrowly scoped to synthetic setup. Verify each warning path and confirm authorized exceptions still post and reconcile.

### H7 · Till credentials and override approval are weaker than main sign-in

**Evidence.** `pos.py:387–408,471–495`, `security.py:153–187`, `web.py:41–45`, `Dockerfile:39`. Overrides verify the manager password directly outside normal sign-in throttling and lockout. The stored approval covers only product and discount percent, although the approval amount is computed using quantity and value. Rate limiting and audit attribution consume the raw forwarded address in `meta_of`.

**Fix and acceptance.** Require an independently authenticated manager or a dedicated step-up flow with the same limits and account checks. Bind the approval to the active shift, register, cashier, canonical cart quantities, prices, amount and explicit expiry. Trust forwarding headers through configured ingress, and rate-limit authentication work before expensive password verification. Verify the approval remains single-use and exact, and Audit can identify both operators.

### H8 · Edge events can be lost from the accounting workflow

**Evidence.** `routes/operations.py:523–545`, `services/sync.py:98–164`, `branch-edge/motion_edge/service.py:137–175,208–259`. Central validates the envelope as a list of dictionaries and commits each event separately. Edge and central lack a shared schema for positive quantities and tenders, timestamp validity and price policy. Invalid and business-rule failures return an acknowledgement without persisting a central reject record. Edge marks a business-rule rejection terminal and has no resolution/retry workflow. Missing acknowledgements can leave a batch looping indefinitely. Unhandled parse or database exceptions can terminate the batch, and a malformed successful HTTP response can escape the edge loop. Replay is keyed by event UUID without checking device and fingerprint.

**Impact.** Goods can leave the shop and be recorded in SQLite while the sale remains unposted centrally. After a transient posting failure or a closed period, Finance lacks a durable central queue to reconcile it.

**Fix and acceptance.** Version and validate the sync contract on both sides, record permanent outcomes durably, and classify transient failures for bounded retry. Add an authorized conflict workflow that retains the immutable event and keeps a clear audit trail. Scope replay to the device and immutable payload, recheck revocation when ingesting, and make every batch return per-event outcomes. Exercise missing acknowledgements, process restart, closed periods, device revocation, duplicate pushes and mixed-result batches. Reconcile local receipts to the central ledger and visible unresolved cases.

### H9 · Edge transport and credential model expose the entire till session

**Evidence.** `sync.py:71–94`, `branch-edge/motion_edge/app.py:1–7,81–121`, `branch-edge/motion_edge/store.py:55–72`, `branch-edge/motion_edge/till.html:70–102`. Deployment guidance binds plain HTTP to the LAN. Edge stores online password verifiers locally and has no explicit restrictive file-mode configuration or login throttling. The till injects catalog, register and receipt text into HTML. Anyone with an edge session receives the latest branch outbox receipts. Manual sync has no operator authorization.

**Fix and acceptance.** Require TLS for tills and central sync, a restricted service account and protected SQLite/WAL/backups, and a separate offline credential or device-bound enrollment with limited lifetime and privileges. Disable pending-password users and derive edge privileges from the same server policy used online. Render all dynamic text through DOM text properties, enforce a CSP, scope receipt history to the cashier or authorized manager, and protect manual sync. Verify revocation/reset, device loss, offline expiry, and secure-context checkout in the target LAN setup.

### H10 · Shift close and checkout do not share a serialization contract

**Evidence.** `pos.py:71–90,124–175,421–424,558–575`. Close locks the platform shift and counts the Tryton session. Checkout and refund read the open shift without acquiring that same guard. The cashier's shift response includes the expected cash total before the blind count. Edge posts with `shift_id=None` (`sync.py:130–133`) and the ledger's cash session is chosen by the Tryton tender path at posting time.

**Fix and acceptance.** Treat the shift-close race as a required concurrency test. Bind online sale and refund to their verified cash session and serialize with close and register takeover. Keep expected totals out of cashier responses before the blind count, and define supervisor visibility explicitly. Decide with Finance which cash custody record receives an event brought back online after a shift closes. Require late events to be traceable without changing a closed count. Run last-unit and close-vs-checkout cases across independent sessions and assertions against till, shift, safe and journal balances.

## Implementation order and code cleanup

1. **Isolate demo and close approval and branch breaches first.** Keep typed request validators at the workflow boundary and SQL row scoping in the query. Introduce negative authorization coverage for detail, list, export, mutation, and derived views. Define a consistent policy for audit, technical admin, and unallocated records.
2. **Reconcile money and inventory under concurrency.** Split `pos.py` into shift, checkout and refund workflows with a narrow internal Tryton posting module. Share inventory guards in the stock domain. Use one idempotency contract for financial writes. Make approval execution and state transitions explicit. Break `purchasing.py` into PO/receipt and invoice/payment workflows with shared, tested receipt allocation.
3. **Make edge recovery and deployment observable.** Split edge protocol/schema, local storage and sync loop. Replace loosely typed dictionaries and terminal catch-alls with typed outcomes. Add schema versioning for existing SQLite stores and alerts for unsynced or rejected receipts. Measure lock pressure and query costs with realistic data, and tune measured hot paths. The insights and dashboards repeatedly compute all-branch stock or several aggregates per request (`insights.py:39–51,80–97`, `dashboards.py:29–38,65–81,108–146`).
4. **Simplify the UI after API contracts settle.** Add typed request/response schemas for the touched routes first. Break `web/src/pages/Pos.tsx`, `Dashboard.tsx` and `Stock.tsx` at existing workflow boundaries. Extract pure totals, permissions and display formatting from JSX. Split `routes/operations.py` into domain routers while preserving public paths. Replace process-global callbacks, globals and private cross-domain helper imports where they obscure transaction order. Remove dead settings, flags and aliases after checking callers. Fix lint findings intentionally, including strict sale-line mapping, with an isolated cleanup commit.

Each PR should identify the findings it closes, the operational behavior it preserves, any migration/backfill, and exact verification results. Keep independent refactors separate from behavior fixes. Use characterization tests for existing externally visible behavior before moving a workflow.

## Release gates

- **Isolation and access.** Credential rotation recorded, isolated synthetic deployment, all three demo/seed switches off on the client deployment, previous demo sessions revoked, privileged MFA, protected edge enrollment, and a verified allow/deny matrix.
- **Finance and custody.** Independently reconcile POS gross/net/VAT/COGS, partial refund totals, safe-to-bank deposits, split tenders, supplier receipts/billing/payments and branch/HQ ledgers. Finance signs off opening balances, period controls and the tax and cash policy. Every posted move balances and every Motion posting has the correct branch or an explicit authorized HQ allocation.
- **Reliability.** Run the suite against real Tryton and PostgreSQL plus Playwright. Run 10 concurrent users including 4 active cashiers on production-sized staging, with concurrent closes/refunds, purchases and reports. Record p50/p95/p99, errors, transaction retries, DB connections and memory. Agree with the operator on acceptable checkout latency and recovery targets, and prove zero duplicate postings or lost receipts. Test WAN outages, restart, database restore, hardware and fiscal-year rollover.
- **Cutover.** Rehearse migration and rollback/forward recovery on a restored copy. Define monitoring and alerts for checkout errors, posting failures, approval exceptions, claims and offline backlog. Start with a supervised branch pilot and reconcile the close before expanding.
